## 4. Frame-200 checkpoint and the B16/L0B16 workload (verified against repository evidence)
* Frame-200 PC reference: captured on x86-32 after 200 real frames at **Thumb PC `0x08000534`, CPSR `0x6000003F`, cycles `56,179,200` (= 200 × 280,896), IRQ entries 191**, inside the 4-instruction VBlank hand-off poll `0x0800052E-0x08000534` (flag `0x03002B64`) (`SMA2_PC_GAMEPLAY_CHECKPOINT_BRINGUP_20261016.md:93`) [V].
* The B16/L0B16 checkpoint (`50282ea4…af32e6`, `SMA2_POST_IRQ_SAFE_CHECKPOINT_20261016.md`) is that state advanced by **76,016 retired guest instructions** to a safe boundary: last retired PC **`0x0809B274`**, next/first PC **`0x0809B276`** (restored R15 and first retired PC in the hardware logs), cycles 56,424,198, VBlank 201, IRQ entries 192. The "0x0809B274" you quoted is the last retired PC; both numbers are correct, they differ by one Thumb instruction.
* Window: **16,384 retired guest instructions** from there to frame 201 at PC `0x08000534`; `native=0`, `interpreter=16384`; 14,075 (**85.9%**) are the 4-instruction poll (3,518-3,519 iterations), 2,309 non-idle, front-loaded in the first ~2,000 (`SMA2_AOT_TWO_FUNCTION_COVERAGE_20261016.md:85-86`); no IRQ delivered inside the window. Timing window ≈ 399,967 µs / 79.99 M cycles (`B16-0x24-hardware.log`) [V].
* Configuration: checkpoint autoload (`SMA2_DEV_CHECKPOINT[_AUTOLOAD]`, path hard-coded `/pc/sma2_checkpoint.bin`, `dreamcast_host_window.inc:48,240-285,305`), `SMA2_SNAPSHOT_H5_DIAG` + `SMA2_SNAPSHOT_H5_TIMING=1` (per-instruction `retire_impl` hook), AOT-bridge dispatch (`cpu_backend=static-recompiled` in the B16/L0B16 logs, **not** force-interp), bridge cap 16 + state-copy deferral + fast miss (`build_q.sh`), L0B16 = generated code linked with a 0-length table (+73-77 ms with zero native execution; `SMA2_AOT_BRIDGE_BATCHING_20261017.md`); hardware ELFs `B16-LOWPMU-sel 60c1289c…`, `L0B16-LOWPMU-sel f40fc020…`.
* Claims in the brief checked: PC `0x0809B274`, 16,384 instructions, 85.9% idle, large I-cache regression with L0B16 native dispatch empty — all **confirmed**. Hardware numbers: B16 ≈ 366-369 ms, L0B16 ≈ 438-441 ms; I-freeze (event 0x24) 24.8 M vs 36.5 M cycles (`SMA2_LOW_PERTURBATION_PMU_HARDWARE_20261017.md`).

**Test ELF vs B16/L0B16 (not layout- or path-equivalent) [V]:** (1) different hot path: test = `runtime_force_interp_step` per instruction (`cpu_backend=interpreter (GBARECOMP_FORCE_INTERP)`); B16/L0B16 = `runtime_dispatch`→`dispatch_resolve`→`runtime_bridge_interpret` (batched) + `retire_impl`; (2) the test ELF has no checkpoint/H5/PMU code (`SMA2_DEV_CHECKPOINT=OFF`, no checkpoint string in the ELF); (3) `.text` 1,154,493 B vs 1,019,044 (B16) / 1,032,708 (L0B16); (4) paths `/cd`-fallback vs `/pc`; (5) different LTO partitioning/function addresses (hash `e81c0f65` vs `60c1289c`/`f40fc020`).
**Can the checkpoint be reached in nullDC3 with the existing test ELF? No.** Missing: a checkpoint-capable build (autoload is compiled out); the loader path is `/pc` only and nullDC3 has no `/pc` (Gate 3C/5 logs); the CDI has no checkpoint file; no `/cd` fallback exists for the checkpoint path. All four need source/build/media work (not authorised here). A cold boot to the same state is plausible (the x86 reference was a cold boot) but unproven for this ELF [U].

## 5. Capture strategies
| | A. breakpoint at repeated loop (`runtime_force_interp_step`/`step_once`) | B. frame-boundary breakpoint (`HostWindow::present .part.0` or hook) | C. guest-PC/checkpoint condition |
|---|---|---|---|
| Reproducible | only if the Nth instruction is chosen: 15-20 M stops [E] | yes: Nth frame, counted by `g_runtime_vblank_starts` | would be exact |
| Startup contamination | first hit = guest instruction 1 | none after frame ≥ a few | none |
| Identifies correct frame | no (no condition support) | yes: read `g_runtime_vblank_starts`, `g_runtime_cycles`, `g_cpu` at each stop | yes |
| Instrumentation | none | none | needs conditional/data breakpoint or checkpoint build |
| Existing RPCs | yes but impractical | yes (`breakpoints.add`, `runUntil`, `getMemorySlice`, `trace.arm`) | no (breakpoints have no conditions; no RAM watchpoints; guest PC is data) |
| Timing/layout risk | none | none (no ELF change) | build change alters layout |
| B16/L0B16 workload | no | no (force-interp path, cold boot) | closest, but still not the B16 bridge path |
**Preferred (B, two-stage, zero source change):** (1) breakpoint on `HostWindow::present .part.0` `0x8C045148`, resume repeatedly, at each stop read `g_runtime_vblank_starts`/`g_runtime_cycles`/`g_cpu` until the target frame; (2) replace it with a breakpoint on `runtime_force_interp_step` `0x8C046B78`, resume, stop at the next **guest-instruction boundary**, verify, arm, remove the breakpoint, resume. This starts the trace at a precise guest-instruction boundary and reuses the Gate 4 recorder unchanged.
**Fallback (no source change):** if `0x8C045148` is never hit, use the hook thunk `0x8C02ECEC`; if neither fires within the bound, stop at `runtime_force_interp_step` after a fixed number of resumed stops only as a *start-of-steady-state* probe (not frame-identified).
**If new instrumentation is wanted (proposal only, not implemented):** a conditional code breakpoint or a memory-value watch on `g_runtime_vblank_starts` in nullDC3, and/or an SMA2 build that autoloads the post-IRQ checkpoint from `/cd` with H5 timing, so the B16 window start (`0x0809B276`, cycles 56,424,198) is reachable deterministically.
